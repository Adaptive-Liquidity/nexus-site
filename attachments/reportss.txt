4. Corrections required before building P1

4.1 Separate capability denial from rollback

This is the most important correction.

The publicly inspectable DemoPlayer’s Abort scenario currently:





Denies NetworkOutbound at Constrain.



Proceeds to a validator result that says rollback is required.



Reports a snapshot rollback.



Describes the outcome as restoring state with no irreversible effect.

That combines two different failure mechanisms into one demonstration. (GitHub)

They should become separate fixtures:

Fixture A — Pre-effect authority denial

Intent
→ Stage
→ Constrain: capability denied
→ Abort / discard staged transaction
→ Emit denial evidence


Expected semantics:





No authorized host effect occurred.



rollback.occurred should not automatically become true.



The snapshot may simply be discarded.



Trust classification: Enforced



Evidence classification: Observed



External-effect absence is not established beyond the governed boundary.

Fixture B — Post-stage validation failure

Intent
→ Stage
→ Constrain: authority granted
→ Apply staged mutation
→ Validate: predicate fails
→ Restore snapshot-backed guest state
→ Emit failure + rollback evidence


Expected semantics:





Staged guest state changed.



Snapshot-backed state restoration occurred.



External effects still require separate analysis or compensation.



Trust classification: Enforced + Observed



External-effect absence remains Not Established unless independently proven.

This distinction should drive all four Observatory lenses.

4.2 Replace broad Abort language

Avoid:

Abort restores pre-execution state. No irreversible effect.

Use:

For this isolated fixture, Abort restores snapshot-backed guest state before any committed effect. External effects require explicit compensation semantics and are not proven absent.

The claims registry already states that Proof Capsules do not prove absence of external side effects and trust the Nexus runtime and host boundary. (GitHub)

4.4 Drive the Observatory from one event stream

Do not separately animate:





a state diff;



capability results;



validator outcomes;



Proof Capsule fields.

Use one immutable sequence:

interface ObservatoryEvent {
  id: string;
  sequence: number;
  stage:
    | "intent"
    | "stage"
    | "constrain"
    | "validate"
    | "decide"
    | "commit"
    | "abort"
    | "emit";
  type: string;
  observedAtMs: number;
  maturity: PublicStatus;
  payloadRef: string;
  evidenceFieldsUnlocked: string[];
}


Each lens becomes a pure projection of:

selected scenario
+ event sequence
+ scrubber time


That prevents impossible states such as a signature appearing before emission or a rollback result appearing before a mutation exists.

4.5 Add canonical, sourced graph relationships

The existing claims registry contains claim rows, evidence, limitations, and status, but does not yet provide the complete relationship topology required by P1. The current Claims page is appropriately registry-driven, searchable, and limitation-preserving, so the graph should augment that dossier rather than replace it. (GitHub)

Every relationship must contain:

interface ClaimRelation {
  id: string;
  from: string;
  to: string;
  kind:
    | "requires"
    | "supports"
    | "binds_context"
    | "blocks"
    | "bounds"
    | "strengthens"
    | "extends_to"
    | "supersedes"
    | "evidences";
  maturity: PublicStatus;
  rationale: string;
  sourceRefs: string[];
  lastVerified: string;
}


Use one direction rule:

from actively relates to to.

For example:

isolation supports transactional-change-gate
stage0-integrity blocks transactional-change-gate
wasm-scope bounds transactional-change-gate
proof-capsule evidences execution-observation


Do not mix active forms such as supports with passive forms such as blocked_by; that creates ambiguous arrow direction.

4.6 Default every mixed-maturity graph to current-only

Where destination architecture appears:

Target nodes are not focusable or announced while hidden.



Revealing targets requires an explicit action.



Target edges remain dashed or patterned.



A permanent text statement explains that targets are non-current.



Current and target distinctions must survive grayscale.

This is particularly important because the claims registry currently classifies the Change Gate and memory binding as In Integration, production signing as Target, and full agent/MCP governance as outside the current WASM boundary. (GitHub)

4.7 Standardize the trust taxonomy

Use exactly four top-level interpretation classes:

ClassificationMeaningEnforcedA runtime or policy boundary actively allowed or denied the actionObservedAn event was recorded, without proving correctness or enforcementResidual TrustThe conclusion still depends on a named host, signer, key, service, clock, or operatorNot EstablishedAvailable evidence does not support the stronger conclusion

Terms such as these remain mechanism descriptions:





denied;



restored;



constrained;



advisory;



degraded;



attested;



compensated.

They should not become competing terminal taxonomies.

4.9 Define manual-versus-scroll arbitration

The hero is both scroll-controlled and manually inspectable.

Without an explicit rule, clicking Validate while the browser remains in the Constrain scroll range may cause the next scroll event to snap the visual back.

Use one of two models:





Clicking a phase programmatically moves to that phase’s scroll location.



Clicking enters a visible Manual inspection mode until the visitor resumes scrolling.

The active control mode should be programmatically announced.
